# Structured Output
The prompt that we give to the LLM was in TEXT format and what LLM gives it is also in TEXT format, but most probably in unstructured form

In LangChain, structured output refers to the practice of having language model return responses in a well-defined data format (for example, JSON), rather than free-form text. This makes the model output easier to parse and work with programmatically.

For example:
[Prompt] - Can you create a one-day travel time table for Paris?
[LLM's unstructured Response]
Here's a suggested time table: Morning : Visit the Eiffel tower
Afternoon: Walk through the Louvre Museum
Evening: Enjoy dinner at a Seine riverside cafe
[JSON enforced output]
[
    {"time": "Morning", "activity": "Visit the Eiffel Tower"},
    {"time": "Afternoon", "activity": "Walk through the Louvre Museum"},
    {"time": "Evening", "activity": "Enjoy dinner at a Seine riverside café"}
]

- Why do we need Structured Output
(i) Data Extraction
    Suppose if we are making Naukri.com website. What key values we can extract from the data would be:
        Name
        10th Marks
        12th Marks
        College
        etc
    And than we can also insert the data into the database easily
(ii) API building
(iii) Agents
    For working with Agents we required Structured Output
    LLM generates the data, while structured output gives that data a predictable format so the agent/application can reliably process and use it.

    1. LLM generates the information

    "What city does the user want?"
            ↓
          Delhi

    2. Structured output tells the program how to interpret/use that information

    {
        "city": "Delhi"
    }

    That's why structured output becomes useful in agentic workflows.


The main reason is when we were getting the information from the LLM. That information was not in the structured form. Due to this we were not able to do many things like Storing the data into the database, APIs, etc.
That's why we require Structured output

- Ways to get structured Output
Structured output means getting the LLM's response in a predefined, structured format so that the application can easily process the data.

There are two particular ways to get the structured output:
    (i) with_structured_output()
    (ii) Output Parsers

Some models supports with_structured_output() and while those who don't than we use the Output Parsers concept. But the modern way is to use the first method

(i) with_structured_output()
with_structured_output() is used to make the model return the response according to a predefined schema/structure.
    LLM
    ↓
    with_structured_output()
    ↓
    Structured Data

It is generally used when the underlying model/provider supports structured output.

(ii) Output Parsers
An Output Parser processes the response generated by the LLM and converts it into the required format.

    LLM
    ↓
    Output Parser
    ↓
    Structured Data

For example:    
    parser = StrOutputParser()
    response = llm.invoke(prompt)
    result = parser.invoke(response)

- How to use with_structured_output()
with_structured_output()
        │
        ├── (i) TypedDict
        ├── (ii) Pydantic
        └── (iii) JSON Schema
(i) TypedDict
Defines the expected keys and their types using Python's TypedDict.

(ii) Pydantic
Defines the structure using a Pydantic BaseModel.
Advantage: It provides validation and gives you a structured Python object.

(iii) JSON Schema
Defines the expected structure using a JSON Schema dictionary.
Advantage: Useful when the schema needs to be represented in a standard JSON-based format.

# TypedDict
It is a way to define the dictionary in python where you specify what keys and values should exist. It helps ensure that your dictionary follows a specific structure

- Why not dictionary?
A normal dictionary only stores data, whereas TypedDict defines the expected keys and their data types, providing a clear structure/schema for the output.
For example:-
    Suppose you and your teammate are working on a project and you have data like this:
        person = {
            "name" : "Amandeep",
            "age" : 21
        }
    The other person can might treat the age data as string. To avoid these things we use TypedDict.

class Person:
    name : str
    age : int

But if we pass age = "24", it would still run. Because TypedDict doesn't necessarily enforced the data type. There is no validation at the runtime if we are using TypedDict(while Pydantic allows validation).


For example:
class Review(TypedDict):
    summary : str
    sentiment : str

structured_model = llm.with_structured_output(Review)

result = structured_model.invoke(
    "The hardware is great, but the software feels bloated. There are too many pre-installed apps that I can't remove. Also, the UI looks outdated compared to other brands. Hoping for a software update to fix this"
)

print(result)
print(result['summary'])
print(result['sentiment'])

Its not magically happening that we are getting the output in a strcutured way.
Behind the scenes -> The llm itself is sending the prompt like this:
    You are an AI assistant that extracts structured insights from text. Given a product review, extract:
        - Summary: A brief overview of the main points.
        - Sentiment: Overall tone of the review (positive, neutral, or negative).
    Return the response in JSON format.

# TypedDict Schemas
TypedDict schemas can progress from simple to more controlled and complex schemas:

TypedDict
    ↓
Annotated TypedDict
    ↓
Literal
    ↓
More Complex Schemas
    ↓
Pros & Cons

(i) Simple TypedDict

The basic version of TypedDict.

from typing import TypedDict

class Review(TypedDict):
    summary : str
    sentiment : str

It tells the LLM:

- summary → string
- sentiment → string

structured_llm = llm.with_structured_output(Person)

But there is a limitation, as we are just passing the attributes name like summary and review. The LLM cannot gurantee that it will always extract the summary from the prompt as we have not given anything extra that "You have to extract the summary"

(ii) Annotated TypedDict
It allows us to attach additional information when we are defining the keys inside the class.
For example:
from typing import Annotated
class Review(TypedDict):
    summary : Annotated[str, "A brief summary of the review"]
    sentiment : Annotated[str, "Return sentiment of the review either negative, positive or neutral"]

The Annotated represents the additional information about what the field/key represents

There is also one more parameter which is "Optional". It can be used with the Annotated and if the required information is not there in the prompt than it will not generate it.
For example:
    class Review(TypedDict):
        summary : Annotated[str, "A brief summary of the review"]
        sentiment : Annotated[str, "Return sentiment of the review either negative, positive or neutral"]
        pros : Annotated[Optional[list[str]], "Write down all the pros inside the list"]
        cons : Annotated[Optional[list[str]], "Write down all the cons inside the list"]
        name : Annotated[Optional[str], "Return the name of the reviewer"]

Since the name is not present it will print "Anonymous"

(iii) Literal

Literal is used when a field should contain one of a fixed set of values.

from typing import TypedDict, Literal

class Review(TypedDict):
    summary: str
    sentiment: Literal["positive", "negative", "neutral"]

The sentiment field is not just any string. It should be one of:

- positive
- negative
- neutral

Example:

{
    "summary": "The product is excellent.",
    "sentiment": "positive"
}

Valid → "positive"

Invalid → "happy"

(iv) More Complex Schemas

We can combine these concepts.

from typing import TypedDict, Annotated, Literal

class ProductReview(TypedDict):
    product_name: Annotated[str, "Name of the product"]
    summary: Annotated[str, "Brief summary of the review"]
    sentiment: Literal["positive", "negative", "neutral"]
    rating: int


# Pydantic
It is a data validation and data parsing library for Python. It ensures that the data you work with is correct, structured, and type-safe.
It is useful when we create APIs
For example:-
We are writing a code in which we validate the "name"

    from pydantic import BaseModel
    class Student(BaseModel):
        name : str

    new_student = {"name" : "Amandeep"}
    student = Student(**new_student) # dictionary unpacking
    print(student)

If we pass integer value, than it will throw an error at the run time

- Default values
We can pass default values also. For example:
    from pydantic import BaseModel

    class Student(BaseModel):
        name : str = "Amandeep"

    new_student = {}
    student = Student(**new_student) 
    print(student)
    print(student.name)

- Optional Fields
This is used when the required information is not there.
    from typing import Optional
    class Student(BaseModel):
        name : str = "Amandeep"
        age : Optional[int] = None

    new_student = {}
    student = Student(**new_student) 
    print(student)
    print(student.name)

- Type coercing
Pydantic automatically converts compatible input data into the type defined in the model.
For example:
    from pydantic import BaseModel

    class Student(BaseModel):
        name: str
        age: int

    student = Student(
        name="Amandeep",
        age="21"
    )

    print(student)
    print(type(student.age))

You provided:
    age="21"
which is a string.

But the model says:
    age: int

Pydantic can convert the compatible string "21" into the integer 21.

- Builtin validation
Pydantic supports many builtin validation. For example:
from pydantic import EmailStr
class Student(BaseModel):
        name : str = "Amandeep"
        age : Optional[int] = None
        email : EmailStr

    new_student = {"email" : "abc"} # It will throw an error
    student = Student(**new_student) 
    print(student)
    print(student.name)

-  Field Functions (default values, constraints, descriptions, regex expressions)
CGPA should be in range between (0 - 10)
from pydantic import EmailStr, Field
class Student(BaseModel):
        name : str = "Amandeep"
        age : Optional[int] = None
        email : EmailStr
        cgpa : float = Field(gt = 0, lt = 10)

    new_student = {"cgpa" : 12} # It will throw an error
    student = Student(**new_student) 
    print(student)
    print(student.name)

We can also give default values. For example:
    cgpa : float = Field(gt = 0, lt = 10, default = 5)

We can add custom descriptions also. For example:
    cgpa : float = Field(gt = 0, lt = 10, default = 5, description = "A decimal value representing the cgpa of the student")

We can add regex expression also for PHONE NUMBER


# Json Schema
It is used when our project is not made using same language
JSON Schema is language-independent, so it is especially useful when different parts of a project are written in different languages.

For example:

Python Backend
     ↓
   JSON
     ↓
JavaScript Frontend

Both Python and JavaScript can understand JSON, and JSON Schema can describe exactly what that JSON should contain.

- Difference
Method	        What we define
TypedDict	    Structure using Python type hints
Pydantic	    Structure + validation using Python classes
JSON Schema	    Structure + types + constraints using JSON
