## 1. What is Persistence?

Persistence in LangGraph refers to the ability to save and restore the state of a workflow over time.

### Concepts Studied

#### (i) Concept of Graph

- A high-level goal is divided into a set of tasks.
- A set of tasks is represented as a graph.
- Every node represents a task.
- Edges between nodes define the execution order.

#### (ii) Concept of State

Before building any workflow, we maintain a state.

- **State:** Important data stored in a dictionary.
- For example, if we are building a chatbot, we can store `"messages"` in the state.
- All the values in the state are accessible to every node.
- Every node can read and update the state.

**State → Every node (R/W)**

## 2. State During Graph Execution

Whenever we invoke a graph, its state is available only during that execution.

Once the graph reaches the end, the state is not automatically saved for the next invocation.

### Example

```text
START
  |
Node 1
  |
Node 2
  |
END
```

## 3. Persistence Using Checkpointers

To retain the state across invocations, we use persistence.

LangGraph uses a **checkpointer** to save the graph's state as checkpoints.

When we invoke the graph again with the same `thread_id`, it can load the saved state and continue the workflow.

### Important Points

- A checkpointer saves the graph's state.
- The saved state can be accessed during a later invocation.
- The same `thread_id` is used to identify the conversation or workflow.
- The graph can continue from its saved state.

## 4. Accessing the History of a Graph

1. Compile the graph with a checkpointer.
2. Invoke the graph for the first time.
3. Use the same `thread_id` when invoking the graph again.
4. Access the history of the previously compiled graph.

### Workflow

```text
Compile Graph with Checkpointer
             |
             v
      Invoke Graph
       (First Time)
             |
             v
      Save Checkpoint
             |
             v
      Invoke Graph Again
       (Same thread_id)
             |
             v
      Load Saved State
             |
             v
     Continue Workflow
```

Working of Persistence
When we use the concept of persistence, it does not save only the "final state values".

It saves "intermediate values" too.

For example:
START
  |
  | State: name = "a"
  |
Node 1 → name: b
  |
Node 2 → name: c
  |
END → Final State (name: c)


It saves intermediate values also.

If the workflow crashes at Node B, LangGraph can use the latest saved checkpoint to resume from that point, rather than restarting from the beginning.

(Biggest advantage - Fault Tolerance)

3. Working of Checkpointers
A checkpointer is a component in LangGraph that saves and retrieves the state of a graph at specific points during execution.

The saved state is called a checkpoint.

In this example, the graph saves the state at four checkpoints:
Step 1: Start — Checkpoint 1
The graph starts execution with the initial state.
numbers = [1]



The first checkpoint is created, and the state is saved.
CP 1 → numbers: [1] → Save


Step 2: Node 1 — Checkpoint 2
Node 1 executes and adds the number 2 to the existing list.
numbers = [1, 2]



The updated state is saved as the second checkpoint.
CP 2 → numbers: [1, 2] → Save


Step 3: Node 2, Node 3, and Node 4
After Node 1, the graph branches into three nodes.

Each node adds a different number to the state.
- Node 2 adds 4.
- Node 3 adds 3.
- Node 4 adds 5.
The nodes are represented as parallel branches in the graph.

Once the branches complete, their updates are combined into the shared state.
numbers = [1, 2, 3, 4, 5]



The updated state is saved as Checkpoint 3.
CP 3 → numbers: [1, 2, 3, 4, 5] → Save


Step 4: End — Checkpoint 4
After all the nodes finish their execution, the graph reaches the End node.

The final state is:
numbers = [1, 2, 3, 4, 5]



The final state is saved as Checkpoint 4.
CP 4 → Final State → Save


4. How Persistence Works
Persistence in LangGraph allows the graph to save and restore its state across different invocations.

The checkpointer stores the graph's state as checkpoints.

If the workflow crashes while executing Node 2, the graph can resume from the latest available checkpoint rather than starting from the beginning.

For example:
START
  |
  v
Node 1
  |
  v
Checkpoint 2
  |
  v
Node 2 → Workflow crashes


When the graph is invoked again with the same thread_id, LangGraph can retrieve the saved checkpoint and continue execution from that point.

This is useful because:
- The graph does not need to repeat all previously completed work.
- The previously saved state is preserved.
- The workflow can recover from failures.
- The graph can resume execution from the latest checkpoint.
Biggest advantage: Fault Tolerance

Threads in LangGraph Persistence
A thread is a unique sequence of graph executions associated with a thread_id. It allows LangGraph to organize and retrieve saved state for a particular conversation or workflow.
How it works
1. First invocation: Invoke the graph with a thread_id, such as "user-123". With a checkpointer configured, LangGraph saves checkpoints for that thread.
2. Next invocation: Invoke the graph again using the same thread_id. LangGraph can load the latest checkpoint and continue with the saved state.
3. Different thread: Use a different thread_id, such as "user-456". This creates a separate state history, independent of "user-123".
Example
config = {"configurable": {"thread_id": "user-123"}}graph.invoke({"message": "Hi"}, config)graph.invoke({"message": "What did I just say?"}, config)



Both invocations use the same thread, so the second can access state saved from the first—provided the graph has a checkpointer and the state is retained in it.

Important: A thread is not an operating-system thread or a single graph execution. It is an identifier for the saved state history across multiple invocations.

Notebook summary: A thread_id identifies a thread in LangGraph persistence. Using the same thread_id lets the graph retrieve that thread’s saved checkpoints across invocations; a different thread_id keeps a separate state history.

# Benefits of Persistence
(i) Short Term Memory
(ii) Fault Tolerance
(iii) Human in the loop (HITL)
(iv) Time Travel

1. Short-Term Memory
Meaning: A graph can remember information from earlier invocations within the same thread.
- The graph saves its state using a checkpointer.
- When invoked again with the same thread_id, it can retrieve the saved state.
- This is useful for conversational applications, where the chatbot needs to remember previous messages.
Example: A user says, “My name is Amandeep.” Later, they ask, “What is my name?” The chatbot can use the saved conversation state to answer.

Remember: Short-term memory in LangGraph is associated with a thread. It is not automatically shared across different threads.
2. Fault Tolerance
Meaning: If a workflow fails, LangGraph can resume from a saved checkpoint instead of restarting from the beginning.
- The graph saves checkpoints as execution progresses.
- If a failure occurs, the latest saved checkpoint can be used to resume execution.
- Work completed before that checkpoint does not necessarily need to be repeated.
Example: A workflow has three steps: Extract → Analyze → Generate Report. If it crashes after Analyze and a checkpoint was saved, it can resume from the saved state rather than repeating extraction.

Remember: The checkpoint must have been saved successfully. Depending on where the failure occurred, the failed step may need to execute again.
3. Human-in-the-Loop (HITL)
Meaning: Persistence allows a workflow to pause and wait for human input, then continue later.
- The graph reaches a point where human approval or input is needed.
- It pauses and saves its state.
- A human reviews the result and provides input or approval.
- The graph resumes using the saved state.
Example: An AI system prepares a purchase order. Before submitting it, the workflow pauses for a human to approve the order. After approval, it resumes and submits it.

Remember: Persistence allows the workflow to retain its state while waiting for the human decision.
4. Time Travel
Meaning: Persistence allows you to access earlier checkpoints and inspect or continue execution from a previous state.

It supports two useful actions:
- Replay: Re-run the graph from an earlier checkpoint, using the saved state.
- Fork: Create a new execution path from an earlier checkpoint, changing the input or state while preserving the original history.
Example: A chatbot gives an incorrect answer. You can return to an earlier checkpoint and replay the workflow, or fork from that point with different instructions to explore another result.

Remember: Time travel does not mean moving through real time. It means revisiting saved graph states and replaying or branching from them.
