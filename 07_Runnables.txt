# Problems that led to LangChain and Runnables

To understand why LangChain introduced Runnables, we need to understand the problems developers faced while building LLM applications.

- Problem 1 — Different LLM providers and different APIs

When ChatGPT became popular in 2022, developers started using LLMs to build different applications.

Initially, OpenAI was one of the major LLM providers, but soon many other companies entered the market, such as Anthropic, Google, Meta, etc.

The problem was that different LLM providers had different APIs and interfaces. Developers had to learn and handle different ways of interacting with each model.

LangChain aimed to provide a common abstraction layer so developers could work with different LLM providers in a more consistent way.

- Problem 2 — LLM applications require more than just an LLM

Developers also realized that building a useful LLM application involves many components, not just an LLM.

For example, consider a PDF Reader application.

To build it, we may need:
    PDF
     ↓
Document Loader
     ↓
Text Splitter
     ↓
Embedding Model
     ↓
Vector Database
     ↓
Retriever
     ↓
    LLM
     ↓
Output Parser

As you can see, there are many different components involved.
So LangChain's idea was:
    Instead of focusing only on the LLM component, let's provide components for the entire LLM application workflow.

Therefore, LangChain introduced abstractions/components such as:
    Document Loaders
    Text Splitters
    Embedding Models
    Vector Stores
    Retrievers
    Output Parsers
    LLMs / Chat Models
    And more
    So where do Runnables come in?

Now we have many different components, and we need a standard way to connect them together.
For example:
    Prompt → LLM → Parser
or:
    Document Loader → Text Splitter → Embedding → Vector DB → Retriever → LLM

This is where Runnables become important.
LangChain provides a common interface for components so that they can be combined, connected, and composed easily.

For example:
    chain = prompt | llm | parser

Here, the components can work together because they follow the Runnable interface.

- Note — Why Chains were introduced

One thing became common in almost every LLM application: creating a prompt and sending it to the LLM.

This process was often repetitive and manual. Developers had to repeatedly perform these steps and connect the output of one component to the next.

So, the LangChain community introduced a new concept called Chain, which allows us to connect multiple components together and automate the workflow.

For example:
    Prompt → LLM → Output Parser

Instead of manually calling each component one by one, we can connect them into a chain:
    chain = prompt | llm | parser

- Disadvantages of Chains
(i) Fixed workflow — follows a predefined sequence.
(ii) Less flexible for dynamic decisions, loops, and retries.
(iii) Complex to maintain when many steps are involved.
(iv) Not ideal for agentic workflows where the LLM decides what to do next.


- Advantages of Chains
(i) Automates workflows — reduces repetitive manual steps.
(ii) Connects components easily — e.g., Prompt → LLM → Parser.
(iii) Reusable — the same chain can be used multiple times.
(iv) Easy to build — components can be connected using |.
(v) Improves consistency — the same workflow is followed every time.

# What are Runnables?
Runnables are like units of work in LangChain.

A Runnable takes some input, processes it, and produces an output.
Every Runnable in LangChain follows a common interface, meaning they provide common methods such as:
    invoke()
    batch()
    stream()

Since Runnables share a common interface, we can easily connect different Runnables together to create more complex workflows.
For example:
    Prompt → LLM → Output Parser

- Types of Runnables
(i) Task specific runnables
(ii) Runnable primitives

(i) Task specific runnables
These are basically existing LangChain components that perform a specific task.

ChatOpenAI
Its job:
    Input → Prompt
            ↓
        ChatOpenAI
            ↓
        AI Response
It performs the LLM call.

PromptTemplate
Its job:
    Input variables
        ↓
    PromptTemplate
        ↓
    Formatted Prompt
It creates/formats the prompt.

Retriever
Its job:
    Query
    ↓
    Retriever
    ↓
    Relevant Documents
It retrieves relevant documents.

So:
    Task-Specific Runnables
    │
    ├── Chat Model → LLM task
    ├── PromptTemplate → Prompt task
    ├── Retriever → Retrieval task
    └── Other LangChain components
Easy way to remember:
    Task-Specific Runnable = A Runnable that performs a particular task.
