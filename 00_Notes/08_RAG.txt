# Introduction to RAG
RAG stands for "RETRIEVAL AUGMENTED GENERATION".
RAG is a a technique that combines information retrieval with language generation where a model retrieves relevant documents from a knowledge base and then uses them as context to generate accurate and grounded responses.
Benefits of using RAG:
    (i) Use of up-to-date information
    (ii) Better privacy (RAG can help organizations use private data without exposing it publicly, but security depends on how the complete RAG system is designed and deployed.)
    (iii) No limit of document size

- Why RAG?

If you use ChatGPT, there are certain things it may not be able to do accurately without access to external or private information. For example:

(i) Latest Current Affairs
If you ask ChatGPT about very recent events, such as information from the past one or two days, it may not provide an accurate or up-to-date response.

This is because an LLM is trained on a specific collection of data and may not have access to the latest information.

(ii) Personal Data
If you ask an LLM to read your personal Gmail messages, it will not be able to do so unless you provide access to those messages through an appropriate integration.
Similarly, if you ask questions about a company's private or confidential data, the LLM cannot answer accurately unless that information is provided to it.

RAG helps address these limitations by retrieving relevant information from external sources or private documents and providing it to the LLM as context.

# Document loaders
There are 100s of document loaders in langchain, but we will study the 4 important ones.
(i) TextLoader
(ii) PyPDFLoader
(iii) WebBaseLoader
(iv) CSVLoader

Document loaders are components in LangChain used to load data from various sources into a standardized format (usually as Document objects), which can then be used for chunking, embedding, retrieval, and generation.

For every document, we have two things: page_content and meta_data.
Document(
    page_content = "The actual text content",
    metadata = {
        "source" : "filename.pdf",
        ...
    }
)


- Why do we need Document Loaders?
An LLM cannot automatically read every file on your computer.
For example, if you have a PDF containing company policies, you first need to:
Read the PDF.
Extract its text.
Convert that text into a usable format.
Pass it to the next RAG component.

The Document Loader performs the first part of this process.

- What is a Document?
After loading, LangChain usually represents the extracted information using a Document object.
A Document mainly contains two things:
    Document(
        page_content="The actual text...",
        metadata={"source": "company_policy.pdf"}
    )

page_content -> Contains the actual extracted text.

metadata -> Contains additional information about the text, such as:
    File name
    Page number
    Source
    Document type

# TextLoader

## Definition

TextLoader (works only with .txt files) is a simple and commonly used document loader in LangChain that reads plain text (.txt) files and converts them into LangChain document objects.

## Working of TextLoader

Text File
    ↓
TextLoader
    ↓
load()
    ↓
Document Object
    ├── page_content
    └── metadata

## Code

from langchain_community.document_loaders import TextLoader

loader = TextLoader(r'file_path', encoding='utf-8')
docs = loader.load()

print(docs)  # It prints a list of documents.

print(docs[0].page_content)

print(docs[0].metadata)

## Using the Loaded Text with an LLM

We can pass the loaded text into the LLM. For example, we can give a prompt:

"Write a short summary on the following document."


# PyPDFLoader (Doesn't work well on scanned data)

PyPDFLoader is a document loader in LangChain used to load content from PDF files and convert each page into a document object.

## Structure

[
    Document(
        page_content="Text from page1...",
        metadata={
            "page": 0,
            "source": "filepath"
        }
    ),
    Document(
        page_content="Text from page2...",
        metadata={
            "page": 1,
            "source": "filepath"
        }
    ),
    ...
]

## Working

PDF File
    ↓
PyPDFLoader
    ↓
documents = [
    Document(page_content="Page1...", ...),
    Document(page_content="Page2...", ...)
]

## Code

from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader(r'filename')
docs = loader.load()

print(len(docs))  # len = Number of pages
print(docs[0].page_content)  # Print 1st page
print(docs[1].page_content)  # Print 2nd page

## Limitations

1. It mainly extracts text, not the complete visual layout.
2. It may not read scanned-based PDFs properly.
3. Tables cannot be read properly.

## Other PDF Loaders

| Use Case | Recommended Loader |
|---|---|
| Simple, clean PDFs | PyPDFLoader |
| PDFs with tables/columns | PDFPlumberLoader |
| Scanned/image PDFs | UnstructuredPDFLoader |
| Need layout and image data | PyMuPDFLoader |
| Want the best structure extraction | UnstructuredPDFLoader |


# DirectoryLoader

It is used to load multiple files from a directory into LangChain document objects.

Instead of loading files one by one (PyPDFLoader), it can load all matching files from a folder.

## Parameters

1. path → Directory path
2. glob → Which files to load
3. loader_cls → Loader to use for each file

For example:

glob = "*.pdf"

with:

loader_cls = PyPDFLoader

would load PDF files from the directory.

## Why use DirectoryLoader?

Without it:

TextLoader("file1.txt").load()
TextLoader("file2.txt").load()
TextLoader("file3.txt").load()

With it:

DirectoryLoader(
    "documents",
    glob = "*.txt",
    loader_cls = TextLoader
).load()

Code:

from langchain_community.document_loaders import DirectoryLoader, TextLoader

loader = DirectoryLoader(
    path = r"E:\Generative AI\07_RAG\data",
    glob = "*.txt",
    loader_cls = TextLoader
)

docs = loader.load()

We can use lazy_load() also:

docs = loader.lazy_load()

for document in docs:
    print(document.page_content)

# WebBaseLoader

It is used to load and extract text content from web pages into LangChain document objects.

## When to Use

For blogs, news articles, and public websites where the content is primarily text-based and static.

## Limitations

1. Doesn't handle JavaScript-heavy pages well (use SeleniumURLLoader for that).
2. Loads only static content.

Code:

from langchain_community.document_loaders import WebBaseLoader

url = "https://..."
loader = WebBaseLoader(url)
docs = loader.load()

print(docs[0].page_content)

# CSVLoader

It is used to load data from CSV files into LangChain document objects.

## Example CSV

name, age, city
Aman, 22, Haridwar
Rahul, 21, Dehradun

Code:

from langchain_community.document_loaders import CSVLoader

loader = CSVLoader("students.csv")
documents = loader.load()

print(documents[0].page_content)

The output for the first row will look roughly like:

name: Aman
age: 21
city: Delhi

So, each row of the CSV generally becomes a Document.


# Text Splitting

Text splitting is the process of breaking large chunks of text (e.g., articles, PDFs, HTML pages, or books) into smaller, manageable pieces (chunks) that an LLM can handle effectively.

## Why Text Splitting?

When documents are large, we cannot efficiently use the entire document as a single unit in a RAG system. Text splitting breaks large documents into smaller chunks.

### 1. Context Window Limitation

LLMs have a limited context window, meaning they can process only a certain amount of text at once.

Large document
    ↓
Split
    ↓
Small chunks
    ↓
Send only relevant chunks

### 2. Better Retrieval

If an entire document is stored as one unit, retrieving information means retrieving the whole document.

Text splitting allows smaller and more relevant pieces of information to be retrieved.

### 3. Efficient Embeddings

In RAG, chunks are converted into embeddings and stored in a vector database.

Smaller, meaningful chunks make it easier to represent and search for specific pieces of information.

## Note

We don't use text splitters because the LLM can't read long documents. We use them so the retrieval system can find the exact match, saving time and money and improving accuracy.

# Text Splitting

## (a) Length-Based Text Splitter (or Character Splitter)

It splits text into chunks based on the length of the text.

Large text
    ↓
Check length
    ↓
Split when limit is reached
    ↓
Smaller chunks

For example:
- chunk_size = 100
- The splitter tries to create chunks of around 100 units of text.

## Disadvantages

1. Can break sentences:
   - It may split a sentence or paragraph in the middle.
2. Can lose context:
   - Related information may be separated into different chunks.
3. Not meaning-aware.
4. Poor for structured documents.

## Code

from langchain_text_splitters import CharacterTextSplitter

text = """
"""

splitter = CharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=0,
    separator=" "
)

result = splitter.split_text(text)
print(result)

## Combining Document Loader and Text Splitter

We can combine the logic of "Document Loader & TextSplitter".

- DocumentLoader is responsible for loading the data.
- TextSplitter is responsible for splitting the data.

result = splitter.split_documents(text)

If 5 pages (PyPDFLoader) are passed, more than 5 documents will be created because each page can be split into multiple chunks.

# Chunk Overlap

Imagine this text:

A B C D E F G H I J K L

Suppose:
- chunk_size = 6
- chunk_overlap = 2

## Without Overlap

- Chunk 1: A B C D E F
- Chunk 2: G H I J K L

## With Overlap

- Chunk 1: A B C D E F
- Chunk 2: E F G H I J
- Chunk 3: I J K L

Chunk overlap means repeating a small portion of one chunk in the next chunk.

# (b) Text-Structure-Based Splitting (or Recursive Character Text Splitter)

It splits text into chunks by trying different separators recursively, while keeping related text together as much as possible.

## Order of Splitting

Paragraph → Sentence → Word → Character

- Paragraph: "\n\n"
- Sentence: "\n"
- Word: " "
- Character: ""

## Note

If the text is too large for one chunk, the splitter tries to split at paragraph boundaries.

If a paragraph itself is still too large, it recursively tries smaller separators.

Long document
    ↓
Split by "\n\n"
    ↓
Still too large?
    ↓
Split by "\n"
    ↓
Still too large?
    ↓
Split by characters

That's why it is called recursive.

## Example

chunk_size = 10

Text:
- My name is Aman (15)
- I am 22 years old (17)
- Paragraph
- I live in Haridwar (18)
- How are you (11)

First, it splits on the basis of paragraphs.

Then, if a chunk is still greater than the chunk size, it splits on the basis of lines.

Then, if it is still too large, it splits on the basis of words.

It can optimize further by joining words when possible.

The resulting chunks can be:
- ["my name is"] ...
- ["Aman"] ...

## Code

from langchain_text_splitters import RecursiveCharacterTextSplitter

text = """
"""

splitter = RecursiveCharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=0
)

result = splitter.split_text(text)

print(len(result))
print(result)


# Document Structure-Based Text Splitting

It divides a document according to its natural structure or syntax, rather than simply splitting it based on character length.

Different types of documents have different structures, so they can use different separators.

## Why Do We Use It?

A normal character-based splitter may break content at an inappropriate location.

For example, in Python code:

class Student:
    def get_details(self):
        return "Student"

Random splitting could break a function in the middle.

Structure-based splitting tries to preserve meaningful structures such as:

Class → Function → Normal Lines → Words → Characters

This helps maintain the meaning and context of the content.

# Different Documents → Different Separators

Each document/language can have its own structural separators:

1. Python → class, def
2. Markdown → Headings, code blocks, horizontal lines
3. Java → Classes, methods
4. HTML → HTML tags
5. Other languages → Language-specific syntax

## Example

from langchain_text_splitters import RecursiveCharacterTextSplitter, Language

text = """
class Student:
    def __init__(self, name, age, grade):
        ...

if student1.is_passing():
    print("The student is passing")
else:
    print("The student is not passing")
"""

splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=300,
    chunk_overlap=0
)

chunks = splitter.split_text(text)


# How Do We Choose Chunk Size?

## Main Real-World Question

Suppose your Markdown is:

# Project Name
A simple Python-based project...

## Features
- Add students
- View students
- Check passing

## Tech Stack
- Python
- No external dependencies

Logically, you may see:
- Section 1
- Section 2
- Section 3

You might think:
"Shouldn't I simply set chunk_size so that I get exactly 3 chunks?"

No.

The number of sections ≠ the number of chunks.

The purpose isn't to force one section into one chunk.

## Main Goal

Create chunks that are:
- Small enough for efficient retrieval.
- Large enough to preserve the context needed to answer questions.

# How Does a Real Application Choose Chunk Size?

There is no universally perfect chunk size.

Instead, you normally follow these steps:

## Step 1: Identify the Data/Document Type

Example:

User uploads document
↓
PDF / Markdown / Python / HTML, etc.

This helps determine the appropriate loader and splitting strategy.

## Step 2: Start with a Reasonable Configuration

For example:

chunk_size = 500
chunk_overlap = 50

These values are starting points, not universal values.

## Step 3: Create Representative Questions About Your Documents

For example:
- Q1: What is the refund policy?
- Q2: Who is eligible?

Then check:
- Did the retriever find the correct chunk?
- Was enough relevant context retrieved?

## Step 4: Evaluate and Adjust

Suppose:

500/50 → Poor retrieval

Try other configurations:

300/50
800/100
1000/10

Then evaluate again.


# Semantic Meaning-Based Text Splitting

It is different from previous methods.

It divides text based on the meaning and similarity of the content rather than using a fixed character length or predefined document structure.

## Why Do We Need It?

Consider this text:

- Python is a programming language.
- Python is widely used in data science.
- NumPy and Pandas are popular libraries.
- The weather in Delhi is hot today.
- Delhi has experienced high temperatures this week.
- A fixed-size splitter might accidentally create:

  Chunk 1 → Python + Python + NumPy

  Chunk 2 → NumPy + Delhi

- But the boundary might pass differently:

  Chunk 1 → Python + Python + weather

  Chunk 2 → NumPy + Delhi

- The chunks may contain unrelated topics.

## Working

This is where embeddings come into the picture.

Suppose we have:

- Sentence 1 → "Python is a programming language."
- Sentence 2 → "Python is used extensively in DS."
- Sentence 3 → "The weather in Delhi is very hot."

The process is:

1. Convert sentences into vectors.
2. For every two consecutive vectors, find similarity.
3. Using similarity, calculate the similarity score (S.D.).

Conceptually:

- Python sentence → `[0.21, 0.72, 0.15, ...]`
- Python sentence → `[0.19, 0.69, 0.17, ...]` → Almost same
- Weather sentence → `[0.82, 0.12, 0.91, ...]` → Different

So, the splitter can use similarity to determine where a new chunk should begin.

## Code

from langchain_experimental.text_splitter import SemanticChunker

text_splitter = SemanticChunker(
    embeddings,
    breakpoint_threshold_type="standard_deviation",
    breakpoint_threshold_amount=1
)

sample = "..."
docs = text_splitter.create_documents([sample])


# Vector Stores

A vector store is a system designed to store and retrieve data represented as numerical vectors.

## Key Features

1. **Storage**
   - Ensures that vectors and their associated metadata are retained.
   - Can be stored in memory for quick lookups or on disk for durability and large-scale use.

2. **Similarity Search**
   - Helps retrieve the vectors most similar to a query vector.

3. **Indexing**
   - Provides a data structure or method that enables fast similarity searches on high-dimensional vectors.

4. **CRUD Operations**
   - Manages the lifecycle of data:
     - Adding new vectors
     - Reading existing entries
     - Updating existing entries
     - Removing outdated vectors

## Use Cases

- Semantic Search
- RAG
- Recommender Systems
- Image/Multimedia Search


# Why We Need Vector Stores?

Suppose we are building a movie recommendation system.

Currently, we have:

Movie API
↓
Movie Data
↓
Frontend

Each movie has information like:
- Title
- Genre
- Director
- Year
- Characters
- Storyline

Now the user clicks on a movie, and we want to recommend movies that are semantically similar to it.

## Problem

If you rely on fields like:
- Genre = Action
- Year = 2024
- Director = X

You may get movies that technically match these fields but aren't actually similar in story/content.

## Solution: Semantic Similarity

Take the storyline of every movie:

Movie A Storyline
↓
Embedding Model
↓
Vector A

Do the same for every movie:

- Movie B → Vector B
- Movie C → Vector C

When the user selects Movie A:

Movie A Vector
↓
Compare with Movie Vectors
↓
Similarity Calculation
↓
Most Similar Movies
↓
Recommendations

## Problem with a Large Number of Movies

Suppose you have 10,000 movies.

You don't want to:

User clicks Movie A
↓
Generate 10,000 embeddings
↓
Compare against everything from scratch

Instead, generate the embeddings once and store them in a vector store.

Then:

User clicks Movie A
↓
Get Movie A embedding
↓
Search Vector Store
↓
Find nearest/similar vectors
↓
Return similar movies
↓
Display them

# Why Not Traditional Databases?

## Traditional Database

→ Find records matching values/conditions.

## Vector Store

→ Find vectors most similar to a given vector.

Vector stores are specialized around vector similarity search, while traditional databases are primarily designed around structured data and traditional query operations.

# Vector Store vs Vector Database

## 1. Vector Store (Storage & Retrieval)

- Typically refers to a lightweight library or service that focuses on storing vectors (embeddings) and performing similarity search.
- May not include many traditional database features like transactions, rich query languages, or role-based access control.
- Ideal for prototyping and smaller-scale applications.
- Example: FAISS.

## 2. Vector Database

- A full-fledged database system designed to store and query vectors.
- Offers additional "database-like" features:
  1. Distributed architecture for horizontal scaling.
  2. Durability and persistence (replication, backup).
  3. Metadata handling (schemas, filters).
  4. Potential for ACID or near-ACID guarantees.
  5. Authentication/authorization and more advanced security.
- Created for production environments with significant scaling and large datasets.
- Examples: Milvus, Qdrant, Weaviate, Pinecone.

## Key Difference

A vector database is effectively a vector store with extra database features, such as clustering, scaling, security, metadata filtering, and durability.
